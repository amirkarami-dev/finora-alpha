1 · System overview

who talks to what

One application, one Docker stack, two companies. Each company has its own API process and its own database, so their data can never mix.

Request path

User's browser CloudflareDNS + TLS (mode: Full) Traefik v3routes on Host header
Traefik
erp.metal-uae.comweb — nginx + SPA
…/api on erpapi (.NET 10)finora
…/api on erp2api2 (same image)finora2
metal-uae.comland — Next.js site

Inside the API — modular monolith

Identity module

Sign-in, session cookie Roles → permissions User admin

ERP module

Contracts, documents Payments, cheques, transfers Warehouse, charges, claims

CMS module

Content for the corporate site
Modules never call each other directly — they talk only through shared contracts (enforced by architecture tests)

Details

  • Front end: React 18 + Ant Design 5, built with Vite. One bundle serves both companies — it calls /api/... relative to its own host.
  • Back end: .NET 10, PostgreSQL 17, Redis. Every write has its own endpoint with a server-side permission check.
  • Errors: every failure is an RFC 9457 problem with a machine code (e.g. invalid-credentials, qty-exceeds-remaining) that the screens react to.
  • Money rules in code: money is decimal, never float; rounding happens in exactly one place, so C# (writes) and TypeScript (reads) agree to the cent.
  • Languages: English, Arabic, Persian with full right-to-left layout. Dark and light theme.
  • Hosting: one compose stack at /data/apps/metal-erp; Traefik + Postgres in a second stack at /data/apps/infra. Postgres has no public port.

Details

  • Session: an HttpOnly cookie — JavaScript cannot read it and nothing is stored in the browser. The cookie is tied to the host, so a login on erp gives nothing on erp2.
  • Permissions come from the server on every load, not from a table inside the app bundle.
  • Sign-out clears the cookie and empties all data held in the browser, so the next person on the same computer sees nothing from the previous user.
  • Seeded accounts: CEO, Manager, Staff and one Customer-portal login per company. Demo passwords work only in development; production needs its own password file or the account is created unusable.
  • Portal scope: which customer the portal login sees is set by the portalAccount flag on exactly one customer.
  • API side: every ERP endpoint also checks the permission itself — the sidebar is a convenience, not the security.

3 · How data moves

reads vs. writes

Writes go to the server one by one. Reads still arrive as one snapshot that the browser computes balances from. This is a deliberate half-way state (the "strangler seam").

On sign-in — reads

Signed in GET /api/erp/snapshotwhole dataset, one request Browser store+ localStorage copy api.ts derives balances, aging, KPIs React Query hooks Screens
API unreachable? Use whatever localStorage holds — the app degrades, it does not go blank

Every save — writes

User saves a form Feature endpointPOST /api/erp/contracts, /payments, … Permission + business rules
valid?
yesPostgreSQLServer-derived fields returned (ids, totals, USD amounts)Store updated, screens refresh
noProblem with a codeToast / message in the user's language

The one exception — demo data

Settings → Load sample / Reset PUT /api/erp/snapshotwhole dataset Erp:AllowDestructiveAdmin on?Replaced
403 — the red "refused" banner; production starts empty and is filled by hand

Details

  • Why one snapshot: a person's balance walks customers, invoices, payments, claims, charges, cheques and transfers together. Moving one entity's reads alone would leave balances quietly wrong, so reads move all at once — a mapped, not yet started project.
  • Server-derived fields (amounts in USD, allocation totals, reference ids) are never trusted from the browser; the server computes and returns them.
  • Known limits of the current state: the whole dataset reaches every browser (the portal hides, it does not filter); a colleague's change is visible only after reload; the maths exists in both C# and TypeScript.
  • Empty start: a new installation has zero records. The full demo dataset lives behind Settings → Danger zone and is centred on today's date.

Details

  • Code (e.g. AM for Alco Metal) becomes part of contract numbers such as AM-P-251101156.

  • Reports: the "Persons" report tab prints one person's movements for a date range.

the deal

A contract belongs to one person and holds one or more goods lines. Each line carries the commercial terms; the product itself is just a name from Base info.

Pricing formula (validated against the original workbook)

unit price (USD/MT) = fixed LME price × (LME % / 100) + premium line value (USD) = unit price × quantity MT AED → USD = amount AED / fx rate (default 3.6725) IQD → USD = amount IQD / fx rate (default 1310, editable per record) Example (Alco Metal, contract AM-P-251101156): 11,685 × 94.76 % + 0 ≈ 11,072 USD/MT

Status

ACTIVEON HOLDCLOSED CANCELLED

Details

  • Two "remaining" figures per line: remaining MT = quantity − shipped in containers (logistics); uninvoiced MT = quantity − confirmed final-chain documents (finance). They are shown apart on purpose.
  • Contract id is built from the person code and the date.
  • Floating lines (LME not fixed) get their LME quotation and date on the provisional or final invoice, not on the contract.
  • Purchase lines may carry partner profit shares (see section 4).
  • Detail page shows the goods table, containers, and every trade document of that contract.

6 · Trade documents

orders → provisional → final

Six types: purchase or sale × order, provisional, final invoice. Created from a contract, converted down the chain.

Pricing an item on a provisional / final document

Copied from contract lineLME %, fixed?, fixed price, premium — read-only LME fixed? Enter LME price + datecan apply to all lines Discount % Line amount in document currency

Details

  • Numbers are assigned by the server: YYMM + 4 digits (e.g. 26090001), one sequence for all six types, restarting each month. Never editable.
  • Currency per document with its exchange rate (1 for USD); totals, discount and weight are stored on the header and recomputed on every item change.
  • Convert creates a new DRAFT of the target type dated today, linked back with a reference. Orders never carry an LME price; PP → PI carries price, date and discount.
  • Remaining per contract line = quantity − Σ chain-leaf confirmed documents of that side, so a PO turned into a PI is counted once.
  • Chain-stable line id survives conversion; payments, claims, charges and warehouse documents all point at it, so they still match after PP → PI.
  • Detail page: reference and "converted to" links, payments recorded anywhere in the chain, print view, "send" marks a sent time.

Stock movement — triggered by confirming a final invoice

Purchase invoice (PI) confirm

Modal: choose target warehouse GRN-2026-0001IN document, CONFIRMED, one line per invoice item Stock += quantity

Sale invoice (SI) confirm

Modal: choose source warehouse Per product: qty ≤ stock in that warehouse? GDN-2026-0001OUT document, CONFIRMED Stock −= quantity
Shortfall → "insufficient stock" with product + available; nothing changes

Stock rule

stock(warehouse, product) = Σ IN − Σ OUT over CONFIRMED warehouse documents product key = name trimmed + lower-cased, so "Copper Cathode" and "copper cathode" are one bucket

Details

  • Warehouse page lists receipts (GRN) and issues (GDN) with their invoice link, warehouse, date and lines; stock per warehouse and product.
  • Warehouses are master data (name, code, location, active). With zero active warehouses the confirm modal explains and blocks.
  • Draft sale invoices show a live "available MT" column per line, coloured when the quantity exceeds stock — the real check is still at confirm.
  • Documents dedupe against the chain-stable invoice-line id, so converting PP → PI never doubles a movement.

8 · Payments and cheques

settling money

A payment has a header, lines and allocations. Only CONFIRMED payments count toward balances. A cheque is a shared record that several payment lines may point at.

Payment status

Header USD amount = Σ line USD amounts (server-derived); the header's control total is checked against the lines

Cheque life-cycle

ChequeNORMAL or SECURITY · number, bank name, due date, amount, owner PENDING PAIDneeds the company account it was banked into RETURNEDEXPIREDCHANGEDreplaced by another

Details

  • Any status may follow any other for a cheque — it describes the real world, which can be corrected. What is guarded is the money: entering PAID demands a live account; leaving PAID drops it.
  • Cheque numbers are unique per bank, not globally — two banks may issue the same number.
  • Chain-aware: payments recorded on a provisional invoice still show on the final invoice it became — no double-pay blind spot.
  • Methods: TT, Cash, Cheque, Offset, Credit Note.
  • Legacy rows without a status are treated as CONFIRMED, never as drafts — otherwise real money would vanish from balances.

9 · Money transfers and exchange gain / loss

company accounts

Two separate ideas on purpose: a transfer moves money between the company's own accounts; a gain or loss records what a currency movement cost or earned.

to amount = from amount × exchange rate (rate = how many "to" units one "from" unit buys)

Exchange gain / loss

Exchange → New Date, signed USD amount, notes Sign of amount GAIN LOSS EGL-0001 …
Deliberately not tied to an account, a rate or a balance — the desk writes the figure down directly. Type is derived from the sign, never chosen.

Details

  • Financial accounts are one entity with a type: BANK (account number, IBAN, SWIFT, address) or CASH_SAFE. Currency is fixed after creation.
  • Transfers appear on the "Accounts" report tab as movements of each company account.
  • History: an earlier revaluation engine (book rates, previews, proportional allocation) was replaced by the simple signed entry, because it answered a question the desk was not asking.
  • Gains and losses flow into the person-independent part of the finance reports.

Details

  • Goods hold only facts about the material. LME %, premium, incoterm and quantity are terms of a deal and live on the contract line — the same good sold twice can carry two premiums.
  • Product name is a reference, not a key: the goods list keeps spelling consistent so reports do not split one product into two rows.
  • One account entity for bank and cash safe, so transfers and payments reference a single id space; the UI still shows two tabs.
  • Unit is MT only. Every quantity in the app is metric tons; adding a unit would touch the pricing maths and every quantity field.
